# Architecture

This document records the live ground-truth verification behind this actor, the mandate corrections that verification produced, and the resulting design. Every claim below traces to a real, observed fetch, browser session, or captured network request made during this build - not to background knowledge or a plausible guess. Where something could not be verified, that is stated explicitly rather than glossed over.

## 0. Live data source verification record

The engineering mandate for this actor asked for a "UAE Mainland Corporate Registry Monitoring Platform" with multi-emirate filtering (Dubai, Abu Dhabi, Sharjah, etc.). Before writing any code, six parallel research passes plus direct, first-hand browser verification were run against every plausible UAE/GCC data source. The mandate's premise only partially holds - **no single, free, anonymous, bulk-queryable open registry exists that covers general commercial licenses across all seven emirates.** What actually exists:

### 0.1 UAE National Economic Register ("Growth", growth.gov.ae) - real, but not usable for this actor

The mandate's implicit assumption of a federal "national economic register" is **factually correct as a named platform** - it exists, is real, and is not a mix-up with Bahrain's Sijilat or Saudi Arabia's Wathq (all three were independently confirmed live and distinct during research). It is officially called the National Economic Register (NER), branded "نمو" (Growth), operated by the Ministry of Economy and Tourism, live at `https://www.growth.gov.ae/G2C/Home`.

However, direct first-hand verification (navigating the live site, not just reading about it) found two disqualifying facts:

1. Its "Open Data" section (`/G2C/OpenData`) contains exactly **7 items**, all legal/regulatory PDF documents (cabinet resolutions, executive regulations) - zero company or license records. Confirmed by directly loading the page and reading its live content.
2. Its actual license-search/export service ("الاستعلام عن الرخص" / "License Inquiry" - which, per its own description, "returns all licenses matching the entered search criteria" and "can be exported to an external file", a genuinely broader capability than a single-record lookup) redirects to `id.moec.gov.ae`, a login page reading "تسجيل الدخول بالهوية الرقمية" ("Login with Digital Identity") with an explicit "Do you need a UAE Pass account?" prompt. **UAE Pass is the UAE's national digital identity system** (biometric/OTP-based, tied to a real person's Emirates ID or passport). This was confirmed by directly clicking through to the service and observing the redirect and page content myself, not inferred from documentation.

A service gated behind a personal government digital identity cannot be automated by an unattended Apify actor - there is no API key or service credential to provision, only a human identity-verification flow. **NER is correctly named in the mandate, but is not usable as this actor's data source.**

### 0.2 Dubai mainland (Dubai Pulse) - the closest real match, but with real access friction

Dubai's Department of Economy and Tourism (DED, formerly DED) publishes exactly the dataset the mandate describes through **Dubai Pulse** (`dubaipulse.gov.ae`), a real, government-recognized (Dubai Data Law) CKAN-style open-data portal:

- `ded_license_master-open` ("License_Master.csv", confirmed via an archived snapshot of the dataset's own column-definition table): `license_number`, `initial_approval_number`, `commerce_register_serial_number`, `chamber_of_commerce_number`, `trade_name_serial_number`, `issue_date`, `expiry_date`, `cancel_date`, `license_status_code`, `license_status_desc_ar`, `license_status_desc_en`, `license_category_code/desc_ar/desc_en`, `issue_authority_code/desc_ar/desc_en`.
- `ded_trade_name-open` ("Trade_Name.csv"): `trade_name_serial`, `trade_name_ar`, `trade_name_en`, `license_number`.

This dataset explicitly covers "the main land of Dubai not the Free Zones" - a direct match for "mainland." It is bilingual, updated weekly, and documented with a queryable `-open-api` REST variant.

**Real access constraints found, honestly documented rather than glossed over:**

1. **Connectivity**: `dubaipulse.gov.ae` rejected every direct connection attempted during this build - `WebFetch` returned `ECONNREFUSED`, a real headless-browser session returned `ERR_CONNECTION_TIMED_OUT`, and two independent third-party proxy services (`r.jina.ai`, `api.allorigins.win`) also failed or returned only a generic homepage shell. Other `.gov.ae` domains (u.ae, growth.gov.ae, id.moec.gov.ae) loaded normally from the exact same tools in the same session, ruling out a blanket "all `.gov.ae` blocked" explanation - this looks like WAF/bot-management or geo/datacenter-IP blocking specific to this domain, which a production deployment would need a UAE-region Apify Proxy configuration to work around.
2. **Access approval**: multiple independent search results tied directly to this dataset's own page describe a **"Request Permission"** gate - "users can agree to terms and conditions and send a request, with confirmation expected within 14 days." This applies to the base CSV tier, not just the API tier. This is not a same-day, self-serve API signup.
3. **Authentication mechanism**: a real (different-dataset) curl example surfaced during research showed `--header "Authorization: <opaque-key>"` with no OAuth token-exchange step - i.e. a single static key sent directly as the `Authorization` header value, not a `Bearer`-prefixed token or a `client_credentials` flow.
4. **Response envelope shape**: could not be confirmed against a real byte of live traffic. `src/dubaiPulseSource.ts` is built from the confirmed column schema but defends against several plausible JSON envelope shapes and throws a specific, loud error if none match, rather than silently returning nothing.
5. **Status-code vocabulary**: the real enumerated values of `license_status_code`/`license_status_desc_en` (e.g. whether "cancelled" reads as a literal string or a numeric code) could not be confirmed. The delta engine never interprets this field into an assumed enum - it tracks the raw description text for equality/change-detection only.

**Given this, Dubai mainland support requires the actor's own end-user to have already completed Dubai Pulse's approval process themselves and supply the resulting key via the `dubaiPulseApiKey` input.** This is the one integration in this actor not verified against live traffic - see the confidence-tier notice at the top of `src/dubaiPulseSource.ts`.

### 0.3 ADGM (Abu Dhabi Global Market) - fully verified, anonymous, bulk

ADGM's public register (`newreg.adgm.com/s/search-results`) is a Salesforce Experience Cloud ("Aura") site. Direct interactive verification (submitting a blank search and inspecting the real network traffic, not just reading the page) confirmed:

- Submitting the search form with a **blank name field** returns "Displaying 1 - 10 of 18745 Results" with full pagination and an "Export as Excel" button - genuine bulk enumeration, not a lookup-by-known-ID.
- The underlying request is a Salesforce Aura RPC call: `POST /s/sfsites/aura?r=N&aura.ApexAction.execute=1`, invoking Apex controller `RASearchUtil.getSearchResponseForPR` with a `jsonSearchString` parameter (captured verbatim from the real request body via a page-level `fetch`/`XMLHttpRequest` instrumentation script).
- **`aura.token=null`** in the real captured request - this endpoint is genuinely anonymous/guest-accessible, no login required.
- A real response row (`0727 HOLDING LIMITED`) was captured directly, giving the exact field vocabulary: `Name`, `Entity_Type__c`, `Incorporation_Date__c`, `Registration_Number__c`, `Entity_Status__c` (e.g. `Registered`, `Deregistered`), `Category__c`, `Entity_Sub_Type__c`, `License_Status__c` (e.g. `Licensed`, `Expired`, `License cancelled`), nested `Addresses__r` and `Trade_Names__r`.
- The request requires a `fwuid` (Salesforce framework build id) and an app-load marker, both embedded in the initial page's `/s/sfsites/l/{urlEncodedJson}/bootstrap.js` resource reference. These rotate whenever ADGM's Salesforce org is redeployed, so `src/adgmSource.ts` fetches the search page fresh each run and regex-extracts them rather than hardcoding a value that would eventually go stale.

This is the most Salesforce-RPC-surface-dependent integration in the actor - more fragile than a documented REST API, since ADGM could change internal field/component names without notice. This tradeoff is accepted because the alternative (no ADGM coverage at all) is worse, and the integration is designed to fail loudly (a clear, specific thrown error) rather than silently misparse if the surface changes.

### 0.4 DIFC (Dubai International Financial Centre) - fully verified, anonymous, bulk, and simpler than ADGM

DIFC's public register page (`difc.com/business/public-register`) loads a **default list of registered entities with no search term required**, confirmed via direct browser interaction. The underlying request is dramatically simpler than ADGM's: a first-party Next.js API route, `POST https://www.difc.com/api/handleRequest`, with body `{name: "", licenseType: "", licenseNo: "", status: "", offset: 0, slug: "/CRM/public-register", method: "POST"}` (captured verbatim via `fetch` instrumentation), returning `{Data: {companyList: [...]}, IsSuccess: true, ...}`.

A real response row was captured directly, giving the field vocabulary: `Name`, `ROC_Status__c` (real observed values: `Active`, `Dissolved`, `Inactive - Struck Off`), `Registration_License_No__c`, `Legal_Type_of_Entity__c`, `Legal_Entity_Type__c`, `ROC_reg_incorp_Date__c`, `License_Activity_Details__c` (semicolon-delimited), `Nature_of_business__c`, `Registered_Address__c`, `Company_Type__c`. No rotating framework id, no bootstrap step, no login - just `offset`-based pagination. This is the actor's most stable integration.

### 0.5 Sources investigated and found not viable

- **Abu Dhabi (ADDED / `data.abudhabi`)**: a real, live, bulk-searchable open-data catalog exists, with genuinely bilingual (Arabic/English) metadata for license-related datasets. But every actual dataset-detail/download page returned a real DKAN/Drupal 404, the catalog's own "Business" domain filter is broken by a live parameter-name bug in the site's own frontend, and the discoverable metadata shows every commercial-license dataset stale since 2023 - not viable for detecting new registrations or status changes going forward.
- **Sharjah (SEDD)**: single-record lookup only (a real license number or trade name is required); no open-data or bulk surface found anywhere on the domain.
- **Ajman (AJDED)**: a genuine, live, browsable open-data portal exists (search, filters, pagination, "Bulk Download") - the most legitimate-looking lead among the Northern Emirates - but every file is a static codebook (legal forms, activity lists, area lists) or a period aggregate report, never a queryable list of individual companies with a status field.
- **Ras Al Khaimah, Umm Al Quwain, Fujairah**: no open-data portal found (RAK/UAQ), or an existing portal that rendered as a completely empty page under automated navigation (Fujairah - flagged as needing manual follow-up, not confirmed non-existent).
- **UAE federal CKAN portals (`bayanat.ae`, `opendata.fcsc.gov.ae`)**: real, genuine open-data portals exist, but every direct fetch attempt against `opendata.fcsc.gov.ae` (five different paths, including the raw CKAN JSON API) returned HTTP 403, a strong, repeated bot/WAF-protection signal.
- **SCA/CMA (Capital Market Authority) and CBUAE (Central Bank)**: both are real, live, paginated, exportable registers (confirmed via a real browser session) - but both are scoped to financial-market/banking-sector licensees specifically, not general commercial entities, and CBUAE's register ships only as a downloadable PDF plus a single-institution search widget rather than a clean list API. Investigated as a possible bonus source but not integrated in this release, given ADGM and DIFC already deliver a stronger, cleaner, general-commerce bonus tier and neither CMA's nor CBUAE's exact request/response mechanics were captured to the same implementation-ready standard as ADGM/DIFC - adding them without that verification would mean guessing a request shape, which this actor's build discipline does not do.

## 1. The resulting scope decision

Given the above, this actor ships with three data sources, each honestly labeled by its real confidence tier:

| Source | Coverage | Access | Confidence |
|---|---|---|---|
| `DUBAI_MAINLAND` | Dubai mainland trade licenses (DED) | Requires the user's own approved Dubai Pulse API key | Schema verified from documentation; wire protocol NOT verified against live traffic |
| `ADGM_FREEZONE` | Abu Dhabi Global Market entities | Anonymous, no setup | Fully verified live (request, response, and field vocabulary) |
| `DIFC_FREEZONE` | Dubai International Financial Centre companies | Anonymous, no setup | Fully verified live (request, response, and field vocabulary) |

`ADGM_FREEZONE` and `DIFC_FREEZONE` are the default-enabled sources (`DEFAULT_DATA_SOURCES` in `src/types.ts`) precisely because they work out of the box with zero setup friction, unlike `DUBAI_MAINLAND`. Abu Dhabi mainland, Sharjah, and the other emirates are not offered as filter options at all - offering a filter for a data source with no real backing would silently return nothing, which this actor's build discipline treats as equivalent to fabrication.

## 2. Bilingual normalization design (`src/bilingualNormalizer.ts`)

Arabic government text is commonly re-exported with inconsistent diacritics, alef/yeh spelling variants, and invisible bidi control characters across otherwise-identical scrapes of the same underlying value. Without normalization, the delta engine would fire spurious `ENTITY_UPDATED` events for a name a human reader would consider byte-for-byte identical. `normalizeArabicText` strips tashkeel diacritics and the tatweel/kashida elongation character, normalizes the four hamza-bearing alef variants (أ إ آ ٱ) to bare alef, normalizes alef maksura (ى) to yeh (ي), converts Arabic-Indic digits to Western digits, and strips bidi control characters (LRM, RLM, ALM, and the explicit embedding/override/isolate ranges).

**A deliberate implementation choice**: every Arabic and bidi-control code point in this module is built at runtime from a decimal numeric constant via `String.fromCodePoint`, rather than written as a literal character or a `\u` escape sequence in the source text. This keeps `bilingualNormalizer.ts` itself 100% ASCII, with zero embedded combining-mark or bidi-control bytes sitting invisibly in the file - the "Trojan Source" class of issues (CVE-2021-42574 and related), where source text can be made to display differently than it executes when it contains raw bidi-control or homoglyph characters. Here the intent is purely defensive (matching and stripping exactly these characters), but the file itself never needs to render right-to-left or invisible characters for a human reviewer or a plain-text diff to verify what it does.

`normalizeEnglishText` canonicalizes UAE-specific legal-entity-suffix punctuation/spacing (e.g. "L.L.C.", "l.l.c", "( LLC )" all normalize to "LLC"; similarly for FZ-LLC, PJSC, PSC, Sole Establishment/Proprietorship, Ltd, Limited) without stripping or reordering the suffix, so two genuinely different companies sharing a legal form are never merged. **A real bug found by this actor's own test suite during development**: the initial regex patterns ended in `\.?\b` (an optional trailing period followed by a word boundary). `\b` requires a transition between a word character and a non-word character; when the matched text's own last character was an optional period immediately followed by end-of-string or another punctuation mark, the regex engine backtracked to *not* consume that period (since consuming it would leave two non-word characters on either side of the boundary, which `\b` cannot match), silently leaving a stray trailing period in the output (e.g. "Acme Trading LLC." instead of "Acme Trading LLC"). Fixed by replacing the trailing `\b` with `(?![a-zA-Z])`, a negative lookahead that has no such requirement.

Neither normalized form ever replaces the raw, original field - both are kept side by side (`commercialNameEn`/`commercialNameEnNormalized`, `commercialNameAr`/`commercialNameArNormalized`), mirroring the fleet-wide convention (Actors #2, #3) of never discarding source data.

## 3. Corrected mandate assumptions

1. **"UAE Mainland Corporate Registry" with multi-emirate filtering is not achievable as a single open bulk source** - see section 0. This actor offers Dubai mainland (with real setup friction) plus two free-zone registers as an honestly-labeled bonus tier, rather than fabricating filter options for emirates with no real backing data.
2. **The UAE National Economic Register, while real, is UAE Pass-gated for its bulk-capable service** and therefore unusable by an unattended actor - see section 0.1. This was independently confirmed by directly navigating the live service, not assumed from its marketing description.
3. **"Officer/manager updates" cannot be tracked.** None of the three verified public sources expose officer, director, manager, or beneficial-owner data in their list/search views - only entity-level status, name, activity, and address fields. `NormalizedEntity` (`src/types.ts`) deliberately does not model officer data; tracking it would require either a paid/authenticated detailed-company-report tier this actor does not have access to, or fabricating a field that does not exist in the real data.
4. **"Activity codes" are largely free text, not a numeric taxonomy**, for the two free-zone sources. ADGM exposes `Category__c`/`Entity_Sub_Type__c` as named categories (e.g. "Non-Financial (Category B)", "Special Purpose Vehicle"), and DIFC exposes `License_Activity_Details__c` as a semicolon-delimited free-text list (e.g. "Holding Company;Managing Office;") - not ISIC-style numeric codes. Dubai Pulse's schema does include `license_category_code`, which is passed through, but its real enumerated values were not independently confirmed (see section 0.2).

## 4. Delta engine design (`src/deltaEngine.ts`)

Every source's raw row shape is mapped into a single `NormalizedEntity` envelope by a per-source `normalize*Entity` function, each validating its own natural key (`license_number` for Dubai, `Registration_Number__c` for ADGM, `Registration_License_No__c` for DIFC) is present and non-empty before proceeding - a malformed row throws a descriptive error and is skipped by the caller (`routes.ts`), rather than fabricating a record identity.

`recordId` is `{dataSource}::{sourceSpecificId}`, guaranteeing no collision between sources even if two different registries happened to reuse the same license number format.

Two independent SHA-256 fingerprints are tracked per entity:

- **`statusFingerprint`**: hashes only `registrationStatus` and `licenseStatus`. A change here means the entity's real-world standing changed (e.g. `Registered` -> `Deregistered`) - the mandate's flagship "detect license status mutations" feature.
- **`contentFingerprint`**: hashes every field except `recordId` itself (matching Actor #3's documented convention - only the record's own identity key is excluded, not every field that happens to also form part of that identity elsewhere). A change here without a status-fingerprint change means a cosmetic edit (address correction, activity-list rewording).

This separation is what lets `classify()` distinguish `STATUS_CHANGED` (the highest-attention event, always notified) from `ENTITY_UPDATED` (delivered and charged, but not pushed to Slack/Teams/webhook, since it's not something a compliance buyer needs to act on immediately) - see `routes.ts`'s `isHighValueChange`.

Because a `StoredFingerprint` only stores hashes, not raw values, recovering *what the status changed from* (needed for both the output record's `previous_registration_status` field and the notifier's "ACTIVE -> SUSPENDED"-style display) requires storing the raw status strings alongside the fingerprints in state - `StoredFingerprint` therefore carries `registrationStatus`/`licenseStatus` directly, not just their hash.

**A second real bug found by this actor's own integration test during development**: `shouldDeliver`'s first implementation hardcoded `ENTITY_UNCHANGED` to never deliver regardless of the `onlyNew` input flag, contradicting this actor's own documented `onlyNew` semantics ("When false, every matched entity is delivered every run... including BASELINE_SNAPSHOT (first run) and ENTITY_UNCHANGED rows" - see `.actor/input_schema.json`). Fixed so `ENTITY_UNCHANGED` and `BASELINE_SNAPSHOT` share the same `!onlyNew` delivery rule, matching the documented and fleet-wide (Actor #3) behavior.

## 5. Retry and error-handling design

All three fetchers (`adgmSource.ts`, `difcSource.ts`, `dubaiPulseSource.ts`) share the same base retry shape: exponential backoff (1s, 2s, 4s, ... capped at 30s) up to 5 attempts, an `AbortController`-based per-request timeout, and a shared `NonRetryableFetchError` class (`src/types.ts`) distinguishing failures worth retrying (5xx, 429, network-level rejections) from failures that would only repeat identically (non-retryable 4xx, an application-level "action failed" response, an unrecognized response envelope). Using a dedicated error class rather than sniffing error-message substrings (an earlier draft's approach) keeps the retry-control-flow signal separate from the human-readable error text that ultimately reaches actor logs, and was itself refined after this actor's own test suite caught two tests timing out because an application-level failure was being retried five times with real backoff delays before the code was corrected.

**2026-09-17 update — `adgmSource.ts` and `difcSource.ts` diverged from `dubaiPulseSource.ts`:** following a live production audit that reproduced genuine, persistent upstream faults (ADGM's Aura backend throwing a server-side `NullPointerException`; DIFC's `/api/handleRequest` returning a live HTTP 500 - both confirmed still failing on direct, independent re-test, i.e. real outages, not a gap in this actor's own retry coverage), `adgmSource.ts` and `difcSource.ts` had up to 30% random jitter added to their backoff delay (`exponential + Math.random() * exponential * 0.3`, matching the sibling TED actor's `tedClient.ts` formula) to avoid a thundering-herd retry pattern across concurrent runs, and their final-exhaustion error now reports the attempt count (`"... failed after 5 attempts: <cause>"`). `dubaiPulseSource.ts` was deliberately left on the original unjittered formula and generic exhaustion message, since it was out of scope for that audit pass (it has no live default-input exposure - `DUBAI_MAINLAND` requires the end user's own Dubai Pulse API key and is not in `dataSources`' default). The three fetchers therefore no longer share an *identical* retry shape, only the same base design; unifying them (or extracting a shared `backoffDelay()` helper, as `tedClient.ts` does) is a reasonable future cleanup but was not applied here to keep that production diff minimal and precisely scoped.

## 6. Testing strategy

135 tests across 11 files. `tests/fuzzing.test.ts` (an explicit mandate deliverable) generates random mixed Arabic/English/bidi-control/astral-plane-surrogate-pair strings via `fast-check` and asserts the full bilingual-normalization and entity-normalization pipeline never throws on any of them (except the deliberate required-field validation, which is itself fuzz-tested to confirm it throws descriptively rather than silently). Two real bugs documented in sections 2 and 4 above were caught by this actor's own unit and integration tests during development, not found later by a separate review pass - `tests/bilingualNormalizer.test.ts`'s LLC-punctuation-canonicalization tests caught the trailing-period regex bug, and `tests/integration.test.ts`'s multi-run lifecycle test caught the `onlyNew`/`ENTITY_UNCHANGED` delivery bug.

## 7. Adversarial review findings

A dedicated 5-dimension adversarial review (data-integration correctness, bilingual-normalization correctness, security, tests/schema accuracy, docs accuracy - each finding independently re-verified by a second pass before being accepted) was run against the completed actor. 9 of 10 raw findings were confirmed real and fixed; the 10th was correctly refuted (a claimed `maxItems`/baseline-completion interaction that, on closer trace, cannot actually occur because `stats.totalPushed` only increments for delivered pushes, and `BASELINE_SNAPSHOT` is never delivered under the default `onlyNew=true`).

1. **HIGH - Slack `<!channel>` mention injection via the unescaped top-level `text` field.** `sendSlackNotification`'s `payload.text` was built from a shared `summaryLine()` helper that interpolated `commercial_name_en` and status fields with zero mrkdwn escaping, while every other Slack-bound field in the same function was correctly escaped via `escapeSlackMrkdwn`. A crafted `commercial_name_en` containing `<!channel>` would have fired a real channel-wide ping. Fixed with a dedicated, fully-escaped `slackSummaryLine()` used only for the Slack payload; the generic webhook's plain-JSON `summaryLine()` is intentionally left unescaped, since escaping it there would show a literal `&amp;` to a consumer expecting the raw name.
2. **MEDIUM - Silent last-write-wins collision in the Dubai trade-name join.** `routes.ts` built its license-number-to-trade-name index with a plain `new Map(tradeNames.map(...))`, silently keeping whichever row happened to be last in the array for a given `license_number` with no logged indication a real DED data collision (an old and a renamed trade name both present) had occurred - unlike every other row-skip path in the same file, which all log a warning. Fixed with a `buildTradeNameIndex` helper that deterministically keeps the higher `trade_name_serial` (the more recently issued trade name) and logs a warning when a collision is detected.
3. **MEDIUM - ADGM's real, live-captured `Trade_Names__r` field was never read.** A trade name's own `Status__c` (e.g. "Active" -> "Inactive") is a genuine status signal, entirely distinct from `Entity_Status__c`/`License_Status__c`, that was silently dropped before ever reaching the delta engine - a real trade-name status change would have classified as `ENTITY_UNCHANGED`. Fixed by adding a `tradeNameStatus` field to `NormalizedEntity` (populated from ADGM's `Trade_Names__r[0].Status__c`; `null` for DIFC/Dubai, which have no equivalent concept), incorporating it into `computeStatusFingerprint`, and threading a matching `previousTradeNameStatus`/`trade_name_status`/`previous_trade_name_status` through `ClassifiedEvent`, `StoredFingerprint`, and `OutputRecord`.
4. **MEDIUM - `normalizeEnglishText` never actually implemented its own documented "( LLC )" example.** None of the `LEGAL_FORM_PATTERNS` regexes matched or stripped surrounding parentheses, so `'Acme (LLC)'` and `'Acme LLC'` normalized to two different strings, capable of firing a spurious `ENTITY_UPDATED` for a name that never really changed. Fixed by wrapping each pattern in an optional `(?:\(\s*)?`/`(?:\s*\))?` pair. **A second bug was found while fixing the first**, before it ever shipped: an initial fix used a bare `\(?\s*` prefix, which happily matches leading whitespace with no paren present at all - this silently ate the ordinary separator space before every unparenthesized legal form too (`"Acme Trading LLC"` -> `"Acme TradingLLC"`, words fused together). Caught by manually re-running the function against all documented cases before considering the fix complete, then locked in with dedicated regression tests (`tests/bilingualNormalizer.test.ts`) for both the original bug and this second one.
5. **MEDIUM - `ActorInput.dubaiPulseApiSecret` was declared but dead.** Present in the TypeScript type, absent from `.actor/input_schema.json` (so no user could ever set it via the Console), and never read anywhere in `src/`. Removed entirely, since Dubai Pulse's real, live-captured curl example authenticates via a single opaque key with no separate secret (see section 0.2).
6. **MEDIUM - The per-row skip-and-continue branches in `processAdgm`/`processDifc`/`processDubaiMainland` had zero test coverage.** `tests/fuzzing.test.ts` and `tests/deltaEngine.test.ts` only asserted the `normalize*Entity` functions throw in isolation; no test ever fed a malformed row through `run()` to exercise the surrounding try/catch/log.warning/continue loop body, so a future refactor that accidentally removed the `continue` or rethrew past the catch would pass unnoticed. Fixed with a `tests/integration.test.ts` case feeding one malformed row alongside one valid row through both ADGM and DIFC and asserting the run completes, skips only the bad row, and still reaches baseline completion.
7. **MEDIUM - `fetchAllDubaiTradeNames` had zero direct test coverage.** `tests/dubaiPulseSource.test.ts` exercised only `fetchAllDubaiLicenses`, and `tests/integration.test.ts` mocks the trade-name fetcher out entirely - a bug isolated to the trade-name endpoint (e.g. a typo in its URL constant) would have gone completely undetected. Fixed with a dedicated test suite mirroring the existing license-fetcher coverage (envelope shapes, 401/403, retry, pagination) against the real function.
8. **LOW - The test suite's default `Actor.pushData` mock returned a bare `{}`, not a real `ChargeResult`.** The real `apify` SDK types `Actor.pushData(record, eventName)` to return `Promise<ChargeResult>` (requiring `eventChargeLimitReached`, `chargedCount`, and `chargeableWithinLimit`); because the `vi.mock('apify', ...)` factory is untyped, TypeScript never flagged the mismatch, so ~90% of `tests/integration.test.ts` exercised an unrealistic return shape that would have masked a regression if `routes.ts` were ever extended to also read `chargedCount`/`chargeableWithinLimit`. Fixed by making the default mock resolve a fully-shaped `ChargeResult`.
9. **MEDIUM - The README's own "real, not fabricated" output-record example had a transcription error.** Both `status_fingerprint` and `content_fingerprint` were shown as 63 hex characters - one digit short of a real SHA-256 digest - while the adjacent `event_id` was correctly computed from the full, correct 64-character values, proving the fingerprints had been truncated after generation rather than pasted verbatim. Fixed by regenerating the example programmatically (writing the actor's real output to a file and having a script splice it directly into the README, with explicit length assertions) rather than hand-transcribing terminal output a second time - the same transcription mistake was caught and corrected once during this exact fix, by a length check catching the same off-by-one before it shipped again.
